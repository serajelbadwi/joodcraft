## 2. هل النتائج كافية للاستخدام؟ — لا، وهذا السبب

**حُجّة «مقبول»:** صورة `medium` أعطت 93.5% — لو كان المُدخل دائماً بذلك النوع (مجلاّت مطبوعة، عمود واحد، بلا تشكيل كثيف) لكان كافياً للاستخدام المُساعِد.

**حُجّة «مرفوض» (وهي الراجحة):**

1. **`easy` هو الواقع.** مستندات JoodCraft عربية، بخطوط مزخرفة، **مُشكَّلة**، وفيها زخارف `❁` وأشرطة وترقيم — وهو نفس نمط الفشل الكامل (28.6%). قِبلة المستخدم لن تكون نسخ PDF نقية.
2. **WER = 100%** على `easy`: لا كلمة واحدة صحيحة كاملة. بلا مسافة يقول: لا يمكن حتى البحث داخل الناتج.
3. **47.65 s/صفحة** يجعل التوليد الجماعي زمنياً مستحيلاً (500 مستند = 6.6 h).
4. **فقدان فراغات الكلمات** (`بأقلُالمقاديرأنالعرب`) في أفضل صورة — يعني أن الناتج لا يصلح حتى لِما بعد المعالجة البسيطة بلا مُصحّح إملائي.
5. **خطأ واحد في حرف** = خطأ في اسم مُتدرَّب أو رقم شهادة. الدقة 93.5% ليست كافية لبيانات إدارية حسّاسة.

## 3. الحجم المتوقّع عند الدمج في Flutter Windows

| طريقة الدمج | الحجم على القرص | الذاكرة | ملاحظة |
|---|---:|---:|---|
| **حزمة Python كاملة** (CPython + paddle + تبعيات + نماذج) | **~796 MB** | 820–970 MB | ما قِيَاس فعلياً. قابل للتنفيذ بـProcess جانبي. |
| **ONNX Runtime عبر FFI** (نماذج مصدَّرة + `onnxruntime` + Dart) | **~150–220 MB** | ~150–300 MB | الأنسب إنتاجياً. يستخدم DirectML/CPU-EP بلا عيب ONEDNN. |
| **ONNX + تجهيز الصور في Dart** (باقة `image` موجودة أصلاً بالمشروع) | **~150–220 MB** | ~150–300 MB | أفضل تحكّم، أعلى كلفة تطوير. |
| **FastDeploy** | ~200–300 MB | ~200–350 MB | مُحسَّن لكن دعم Windows/CPU محدود، ويحتاج FFI كذلك. |
| **خدمة Python محليّة (HTTP)** | ~796 MB + خدمة | 820–970 MB | أسهل ربطاً، لكن يبقى ثقيلاً وبطيئاً. |

**توفير ممكن في الحالتين الأخيرتين:** إسقاط نموذجَي `UVDoc` (30.8 MB) و`PP-LCNet_x1_0_doc_ori` (6.6 MB) إن لم نحتج تصحيح تفتّح المستند ⇒ **~98 MB نماذج فقط** (كشف + تعرّف عربي + اتجاه سطر). تظهر هنا ميزة ONNX: تختار نموذجاً نموذجاً، بخلاف الحزمة التي تُنزّل الخمسة كلّها.

## 4. أفضل طريقة دمج (إن تمّ)

## 🥇 ONNX Runtime عبر FFI + تجهيز الصور في Dart

- نقل `PP-OCRv5_det` و`arabic_rec` إلى ONNX، ثم استدعاؤهما من Dart عبر حزمة `onnxruntime` (أو C API مباشرة).
- كشف → قصّ → تدوير → تعرّف: كلّ ما بعد القصّ يُنفَّذ في Dart (الباقة موجودة: `image`).
- **لماذا:** أقلّ حجمًا (≈150–220 MB)، أقلّ ذاكرة، ولا يمرّ بعيب ONEDNN، ويتوافق مع تحزيم Flutter Windows الحالي.
- **الكلفة:** تحويل النماذج + كتابة كشف اللاحق (NMS، فكّ الترميز العربي) في Dart.

| 🥈 Python جانبي (sidecar) | 🥉 خدمة HTTP محلية |
|---|---|
| ~796 MB، أبطأ، لكن **جاهز اليوم** — مناسب كـProof-of-Concept فقط | أسهل ربطاً وأضعف نضجاً لإنتاج |

## 8. ما الذي قد يغيّر القرار؟

1. **تجربة ONNX (1–2 يومان):** إن أنتجت < 3 s/صفحة، يتغيّر تقييم الأداء جذرياً ويصبح المسار B جذّاباً.
2. **تجربة دمج الصناديق وإعادة الترتيب (أسبوع واحد):** الأرخص والأعلى مردوداً. `hard` يُثبت أنّ **86.3% من الكلمات تُتعرَّف فعلاً** مقابل دقة 63.2% — أي أنّ 23 نقطة تضيع في التقطيع لا في التعرّف. مُصحّح ترتيب بسيط قد يرفع `hard` إلى ~85%.
3. **مُدخل مقيد:** إن كان الاستخدام «استخراج أسماء من جداول نظيفة فقط» (`medium` ≈ 93.5%)، فالدمج قد يكون مقبولاً كأداة مساعِدة لا كأداة إنتاج نهائي.
4. **تنظيف مُسبق للصورة:** ✅ **قِيَاس فعلاً — واللون ليس السبب.** إسقاط اللون (`gray`) والت threshold (`bin`) لم يُغيّّرا شيئاً (28.6%→28.2%→27.5%)؛ إبقاء الحبر الداكن فقط (`dark`) أعطى **+4.1 نقطة** (32.7%) لأنه قتل ضجيج الزينة لا المشكلة نفسها.
5. **عيّنة مُوسَمة من JoodCraft:** بلاها لا يُحسم أيّ تقدير دقّة حقيقي على مُدخلاتنا.
